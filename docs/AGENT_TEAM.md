# ทีมช่วยสร้างเกมจากความคิดของผู้เล่น

ทีมใช้ repository เดิมเป็นฐานเดียว อ่านความต้องการร่วมกันและแบ่งงานตามผลลัพธ์
ไม่ต้องสร้าง repository แยกสำหรับทุกบทบาท เมื่อมีเครื่องมือใช้ซ้ำหลายเกมจริง
จึงค่อยแยก package/repository โดยรักษาการอ้างอิงเวอร์ชันไว้

## บทบาทและ skill

| บทบาท | รับผิดชอบ | Skill ใน repository |
|---|---|---|
| ผู้ประสานความคิด | แปลงคำพูดผู้เล่นเป็นงานที่ดู/เล่นได้ จำความต้องการและรวมผลงาน | [dream-game-director](../.agents/skills/dream-game-director/SKILL.md) |
| ผู้ออกแบบภาพ | ตัวละคร ฉาก การ์ด องค์ประกอบ แสง ฟอนต์และการตอบสนอง | [game-art-direction](../.agents/skills/game-art-direction/SKILL.md) |
| ผู้ออกแบบการเล่น | คอมโบ ศัตรู เหตุการณ์ รางวัลและการตัดสินใจที่ต่างกัน | [roguelike-content-design](../.agents/skills/roguelike-content-design/SKILL.md) |

## วิธีรับงาน

1. ผู้ประสานอ่าน [PLAYER_VISION](PLAYER_VISION.md),
   [DECISIONS](design/DECISIONS.md) และ [CURRENT_TASK](design/CURRENT_TASK.md)
   แล้วใช้คำขอล่าสุด ไม่มีการให้ผู้เล่นกรอก specification ยาว ๆ
2. แปลงเป็นผลที่ตรวจดูได้ เลือกเฉพาะบทบาทที่ช่วยงานนั้น โดยทั่วไป 2–4 งานย่อย
3. ส่ง [handoff](../.agents/skills/dream-game-director/references/handoff.md)
   พร้อมเจ้าของไฟล์ชัดเจน งานค้นและออกแบบทำคู่ขนานได้ งานรวมภาพ/โค้ดตาม dependency
4. ผู้ตรวจตรวจผลงานจริงและแจ้งช่องว่าง ผู้พัฒนาแก้ตามขอบเขตที่รับผิดชอบ
5. ผู้ประสานส่งภาพ/เกม/ไฟล์ที่เกี่ยวข้อง อธิบายผลภาษาผู้เล่นและอัปเดตความจำ

เมื่อมี collaboration tools จะเรียกเอเจนต์ย่อยจริง ถ้าไม่มี ผู้ช่วยทำแต่ละหน้าที่
ตามลำดับได้ skills เป็นคำสั่งทำงานใน repository ไม่ใช่ agent process ที่เปิดค้าง
และไม่ได้ติดตั้ง API/plugin หรือฝึกน้ำหนักโมเดลเพิ่ม

## ความจำและการตัดสินใจ

ผู้ประสานเป็นผู้เขียน shared memory คนเดียว Workers ส่งข้อเสนอและผลตรวจกลับ
ผู้ประสานเป็นผู้ถามผู้ใช้คนเดียว รวมคำถามจากทุกบทบาท ไม่เกิน 1–3 ข้อต่อรอบ
เอเจนต์ย่อยไม่ส่งแบบสอบถามแยกกันจนผู้ใช้ต้องตอบเรื่องเดิมหลายครั้ง
แยกสิ่งที่ผู้ใช้ยืนยัน / ข้อเสนอที่ใช้ลอง / สิ่งที่ตรวจพบจาก source ให้ชัด
คำตอบล่าสุดของผู้ใช้แทนที่ข้อตกลงเดิม ไม่สร้างเงื่อนไขซ้ำหรือถามคำถามเดิมใหม่

เรื่องที่ขาดแต่ตัดสินใจย้อนกลับได้ให้เลือก default ที่มีเหตุผลแล้วแสดงผล
เรื่องรสนิยมสำคัญให้เสนอภาพเปรียบเทียบสองหรือสามแบบและถามสั้น ๆ เมื่อจำเป็น
การให้ดูตัวอย่างไม่บังคับให้ผู้ใช้อนุมัติทุกงานก่อนทีมลงมือ
ข้อมูลบัญชี/การเปิดบริการจริงใช้บัญชีของผู้ใช้และขั้นตอนที่จำเป็นตามขอบเขตงาน
ไม่ขอรหัสผ่านหรือ keys ส่วนตัวในแชต

## สิ่งที่ต้องส่งให้ผู้เล่นตรวจ

| คำขอ | ผลขั้นต่ำที่ตรงคำขอ |
|---|---|
| งานภาพสวยขึ้น | ภาพจริง/ทางเลือกที่มีงานภาพ; เมื่องานคือแก้เกมต้องรวมภาพในเกมและส่ง runtime capture/APK |
| เล่นสนุกขึ้น | ตัวอย่างการเล่นที่ทางเลือกเปลี่ยนผล คอมโบมีต้นทุนและข้อแลกเปลี่ยน พร้อม feedback |
| เนื้อเรื่อง | ธีม/ฉาก/เหตุการณ์ที่ใช้ในเกมและแหล่งอ้างอิงเฉพาะส่วนที่เกี่ยวข้อง |
| เกมบนมือถือ | native UI ที่ตรวจได้และ APK; แยกผล Linux/static export จาก Android device |
| บัญชี/เซฟออนไลน์ | source/config ที่ตรวจแล้วและขั้นต่อบัญชีบริการจริง; ไม่เรียก fixture ว่า deploy |
| ขอทีม/skills | ไฟล์ความจำ บทบาท handoff และตัวอย่างรับคำขอ; ระบุว่าไม่ได้เปลี่ยนเกมในรอบ setup |

จำนวน agents, skill files, การ์ดหรือ tests ไม่ใช่คะแนนความสวย/ความสนุก
การรับช่วงใหม่ต้องอ่านไฟล์เหล่านี้ โครงการอื่นและแชตที่ไม่ได้อ่าน repository
ไม่ถือว่าได้ความจำนี้โดยอัตโนมัติ ดู [คู่มือคุยกับทีม](MAKE_MY_GAME.md)
และ [ผลตรวจ workflow](design/WORKFLOW_VALIDATION.md)
